# observed/

Phone results: the test reports the OCD Check app uploads through the `OCD Check report` issue form, as unverified hints, and the owner's settled results as "re-tested by OCD". [community/README.md](../community/README.md) describes the path.

| Path | Contents |
|---|---|
| `reports/issue-N.json` | one valid report per issue, as submitted (`schemas/ocd-check-report.schema.json`), with its issue number, report date, SHA-256 hash, release, tester (`owner` for the owner's account, else `outside`), `"verification": "unverified"` and its status after the noise filters (`counted`, `held`, `superseded`, `duplicate`, `expired`) |
| `summary.json` | the reports of every account but the owner's, per device × carrier profile × stack × entry: "reported, not checked by OCD", "contested" and the held reports; its "re-tested by OCD" is always null (`schemas/observed-summary.schema.json`) |
| `retested.json` | the owner's phones' settled results as "re-tested by OCD" records (rule round 29): pointers with a result class, level, bearer, method, the cell with the ROM build, n, the first and last day measured, the data commit with its data digest, and an expiry 90 days after the last measurement (`schemas/observed-retested.schema.json`) |

**People's reports are unverified.** A report only points at an entry of OCD's data at one commit of `main`, or of a data release for older app builds (`volte:on`, `apn:<row key>`, ...); it never carries a value. It never changes an OCD value, a file under `carriers/` or `generated/`, or a release, and it never makes a phone skip its own test: at most a phone tests that entry earlier. The owner's settled results in `retested.json` are measured on his own phones and read "re-tested by OCD"; they too are pointers, never values, never change a configured value, and on another phone only move a test earlier. A correction or a measured failure there opens a source-review issue. This folder is not a release asset. The files are written by `tools/observed_reports.py` from the report issues; do not edit them by hand. The `validate` check fails when a file breaks its schema or the privacy scan, or when `summary.json` or `retested.json` is not what the reports give.
