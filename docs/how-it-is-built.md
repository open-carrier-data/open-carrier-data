# How the data is built

This page explains where a carrier profile comes from and why it looks the way it does. It is not a command reference. For commands, read [consume.md](consume.md).

## The pipeline in one picture

Every value in `carriers/open/` passes through the same five stages:

```text
source families          upstream repos, vendor indexes, firmware baselines
      |
candidate observations   private normalized records, one per source and carrier match
      |
the sanitizer            merges, quarantines, and strips private material
      |
carrier profiles         neutral JSON in carriers/open/, one file per match set
      |
generated files          generated/index.json, evidence-index.json, android/, devices/
```

The first three stages live in the private repo. Since 2026-09-24 a weekly GitHub-hosted job runs them for every source family except Samsung, whose lane needs firmware downloads and pinned image tools that only a self-hosted runner has. Since the same day that runner is back on the owner's machine as a user service, and the Samsung lane runs daily at 02:00 UTC in one bounded unit: up to 2,048 firmware update server probes and 50 selective CSC extractions, then a date refresh of every observation whose firmware build was confirmed current. The public repo receives carrier profiles and generated files, then its own workflow validates them. The public tools can regenerate `generated/android/` from the profiles, but they cannot rebuild profiles from sources.

## Sources become candidate observations

A source family is one upstream. Examples are the LineageOS APN repo, Apple's carrier bundle index, or a Samsung firmware baseline. An importer reads the upstream and writes candidate observations. Each observation records one carrier match set, the facts seen, the source family, the upstream revision, the date automation checked it, and, where it can be found, the date of the newest upstream entry behind it. Raw source material stays in the private repo.

Samsung's IMS and CarrierConfig values come from one build of the newest One UI branch; the older branch differs mostly in entries Samsung later removed or reworked.

[SOURCES.md](../SOURCES.md) lists every source family and its terms.

## The sanitizer merges observations into profiles

The sanitizer groups observations and applies fixed rules. The rules are:

- Grouping by exact match set. Observations with the same `mccmnc`, `spn`, `gid1_prefixes`, `gid2_prefixes`, `iccid_prefixes`, `imsi_prefix_patterns`, and `android_carrier_ids` form one profile. A different match set forms a different profile. The `spn` comparison ignores letter case, so `TELEKOM` and `Telekom` land in one profile. The profile keeps the spelling the most independent source families give, then the one from the higher naming authority (the order below), then the first in character order; observation counts play no part, so a profile ID does not change when a firmware run adds or expires observations.
- Naming. A display name never changes a profile: `profile_id` is a hash of the match set alone. Names are ranked in three steps, with words like `internet` or `mms` stripped before they are compared. First the kind of source: any operator-facing name (AOSP's carrier list, Google CarrierSettings, Apple's bundles, GNOME's provider list, the AOSP-derived APN lists, Samsung's OMC carrier packs) beats Samsung's IMS profile names, which are internal labels such as `GenericIR92 US CSpire` or `Dish US`. A label is used only when nothing else names the match set. Then the number of distinct source families behind the name: the two Google lanes count as one, and so do the LineageOS, Sony and Fairphone APN lists, which copy AOSP's list. Observations are not counted, so duplicate firmware builds, models or Pixel devices cannot win a tie. Equal support falls to a fixed order of naming authorities: Apple's bundle names, Samsung's OMC network names, AOSP's carrier list, Samsung's carrier table, GNOME's provider list, the APN-list labels, and last Google's canonical identifiers such as `tmobile_us`. Before any ranking, candidates that name no carrier are left out: an empty name; "Carrier", "Default", "Unknown" or "Generic", alone or with a number; Google's private-network template `pn_xx` (1,099 MCC 999 profiles, now `Carrier 999xx`); an importer's fallback such as `LineageOS 26202`; a name with `=`, such as Google's selector identifiers `26201Spn=Debitel` or `310410Gid1=60Ff`; a network code alone, also with a country code (`26203`, `26214 De`); and a bare APN label such as `Internet`. Only a profile with no candidate left gets the neutral `Carrier <mccmnc>`. The winning name is then published in its cleanest spelling among the candidates that are the same name apart from case, punctuation, APN words or a trailing country code: without an APN word, without a country code, not all lower case, without underscores, then by naming authority. So `o2-de`, `o2 - de` and `O2 De` become `O2` where a source writes `O2`, and `O2 De` where none does. Every published spelling is one a source gives. Spellings of one name do not add to its support. Entry dates do not choose a name: they date the settings around a name, not the name, so they cannot tell a retired brand such as `E-Plus` from a name whose settings have not changed.
- Agreement. When every source that names a fact gives the same value, the value is published. An off for a capability, or a false capability switch in CarrierConfig, also needs the evidence described below.
- Conflict omission. When sources give different values for one CarrierConfig key or one add-on key, the value is left out. The evidence index records the conflict with `resolution: omitted_from_stable`. One exception: a false that one non-operator family alone gives for VoLTE, Wi-Fi calling or video calling is left out before this test, so it does not withdraw another observation's true, see Capability switches in CarrierConfig below. Two keys are compared as sets, because Android reads them into a set: `carrier_metered_apn_types_strings` and `carrier_metered_roaming_apn_types_strings`. The same APN types in another order are not a conflict, and the value keeps the order of the first source that gives it.
- APN variants. When sources disagree on one APN selector, every variant is published, because an APN list holds several rows per type by design. The evidence index records the conflict with `resolution: published_variants`. Rows that differ in proxy, port, username or password are separate rows, a missing value meaning none, and a source backs a row only when it gives the same four values: one source's proxy or credentials are never filled into another source's row. For a row's `mms` type the MMS proxy and, with an MMS proxy, the MMS port count too, because the MMS service sends through them: a source backs an MMS row only when it gives the same MMS proxy and port. An MMS port without an MMS proxy does not count, and for other types the MMS settings merge as before. Other attributes, such as the protocol or the MMSC, still merge into one row when the sources do not disagree. A profile lists its rows by APN. The Android files order them by the evidence behind each row, see [How the Android APN file is ordered](#how-the-android-apn-file-is-ordered).
- Usable APN values. The sanitizer removes control characters and surrounding whitespace from every APN string, SPN and display name, so Google's SPN `C Spire\r` is the same profile as `C Spire`. An MMSC without a scheme gets `http://`, because Android's MMS service opens it as a URL, and `http:/host`, `http//host` or a space after the scheme are repaired. `null`, `none` and a bare `http://` mean no MMSC. A `*` type means what Android reads from it, `ApnSetting.TYPE_ALL`: `default`, `hipri`, `mms`, `supl`, `dun`, `fota`, `ims` and `cbs`. The validator refuses a profile that breaks any of these rules.
- MMS rows need an MMSC. Android's MMS service looks the MMSC up among the SIM's `mms` rows with the APN its MMS connection uses. So a row typed `mms` without an MMSC keeps the type only when another `mms` row of the same APN and MVNO selector carries one. Otherwise it loses `mms`, and a row that served only MMS is dropped. An MMSC with a brace, whitespace or a non-ASCII character is not a URI and states no MMSC, because the phone, not the modem, parses it; a row that carries one loses `mms` even when another row of its APN carries a good MMSC. That keeps out Samsung's Yoigo row with Google's home-page template `http://www.google.com/m?client={CID}&source=android-home` and Tattelecom's `https://mmsс:8002`, whose `с` is Cyrillic (rule decisions of 2026-10-13, round 13). The evidence index records the `mms_without_mmsc` gate. The validator refuses an `mms` row whose APN has no MMSC in its profile.
- Empty APNs are not published. An `ia` row with an empty APN asks the network to pick the APN, and no source says why its rows are empty; an empty APN on any other row cannot work. Every importer drops such a row. [consume.md](consume.md#rows-with-an-empty-apn) says what Android does instead.
- Empty profiles are dropped. A profile left with no APN, no CarrierConfig, no add-on, and no known capability is not written. The sanitization report counts these as `empty_profile_count`.
- Conditional capabilities. Capabilities are the one exception. A disagreement becomes `conditional` instead of an omission.
- Google's current file supersedes its frozen copies. Google's file for a Pixel it no longer updates (Pixel 1 to 5a), or an older snapshot of a current Pixel's file, read from TheMuppets' frozen Pixel trees (`google_pixel_vendor_carriersettings`), is a superseded revision of Google's carrier settings. It counts for a capability or a CarrierConfig key only where Google's current file (`google_carriersettings`) gives no value; where the current file gives one, the frozen copies are left out for that key before any other rule. A conflict they alone caused is recorded with `resolution: superseded_device_file`, and `capability_sources` and `capability_newest_entries` follow the published value. This is the same reason Samsung's IMS table is read from the newest One UI branch only and the APN ordering puts a current vendor's row first. Measured on 2026-10-09, another family agreed with the current Google value in 223 of 223 capabilities and 343 of 343 CarrierConfig values this settles, and with the frozen value in none. About one in five of those capabilities was Google keeping a feature off on an old Pixel, which gets no more updates. Disagreements between current devices, between device trees, between a frozen tree of another maker and LineageOS, and between families are not settled by dates: they stay `conditional`, or the CarrierConfig value stays left out, except a VoLTE, Wi-Fi calling or video calling switch whose false one family alone gives, see Capability switches in CarrierConfig below.
- One maker's off is not proof. A maker's or maintainer's carrier table that turns a feature off says how their phones are set up, not that the carrier lacks the feature. So a capability is `unsupported` only when the operator's own configuration turns it off, or at least two independent source families turn it off and none turns it on. An off from one family alone is published as `unknown`, and the evidence index records the gate `single_family_off:<capability>`. Against an on, it makes the value `conditional`, except for VoLTE, Wi-Fi calling and video calling where every such off is an `off` device record (see Device records next to the carrier value). The LineageOS, Sony and Fairphone APN lists count as one family, as do the two Google lanes and Samsung's three lanes (OMC, IMS and CarrierConfig), the same grouping the APN ordering uses. Samsung's and Apple's offs never count. Both write an off almost always as a missing entry: 3,622 of 3,674 offs in Samsung's tracked IMS table, and most iPhone bundles. Their written offs describe phones or defaults, not the carrier: measured on 2026-10-09, Samsung's written table offs agreed with another family's off in 2 of 9 comparable cases, Samsung's phone-pack offs in 0 of 31, and Apple's written falses in 0 of 12. A carrier pack's off, including a carrier-branded pack's off for its own SIMs, describes the phones that use the pack; it is not published. On 2026-10-06 that kept VoWiFi `supported` on the 16 Spectrum and Xfinity profiles whose branded Galaxy packs switch it off on some models.
- The operator's own configuration. A carrier pack, branded or not, is maker configuration. Two kinds of source count on their own, and only where it was checked: Google's CarrierSettings for its own Google Fi service (Google's carrier names `fi_us`, `fi_tmo_us`, `fi_extended_us`, `fi_at` and `fi_es`), and an AOSP CarrierConfig file whose git history shows the carrier wrote it. On 2026-10-04 that is one file, SETAR's (carrier ID 493, Aruba): both commits that wrote it are by SETAR staff. The other AOSP offs were written by Google staff and count like any other source.
- An ended service stays as the tables say. When an operator ends a service, phone makers' tables often keep it for months or years: on 2026-10-09 Google's current file and all current Samsung observations of their base profiles still configured MMS for Telekom, O2 and 1&1 Germany, which ended it on 30 June 2026. OCD publishes what the tables configure and does not track service status, so such a value stays `supported` and its APN rows stay; on Android a missing MMS row does not make MMS work, it only changes how a send fails.
- Capability switches in CarrierConfig. A false value of a key that switches a capability off on the phone is left out when one non-operator family alone sets it, so a ROM that applies the profile does not switch the feature off on that family's word. The evidence index records the gate `single_family_off:<key>`. The keys are `carrier_volte_available_bool`, `carrier_wfc_ims_available_bool`, `carrier_vt_available_bool`, `enabledMMS`, `imssms.sms_over_ims_supported_bool`, `support_ims_conference_call_bool` and `support_conference_call_bool`. No other key is affected, and true values stay. For `carrier_volte_available_bool`, `carrier_wfc_ims_available_bool` and `carrier_vt_available_bool`, which Android reads as false when they are missing, such a false also does not withdraw a true that another observation sets: withdrawing the key as a conflict would switch the feature off on the same family's word. Since 2026-10-10 the true is published against one family's off, unless the old single-source rule below would withhold the true observations standing alone; then the key stays left out as a conflict. The capability stays `conditional`, because the sources disagree, and `capability_sources` lists the off, unless every off is an `off` device record; then it is `supported` (round 17, step 2, below). An off from the operator's own configuration or from two families still withdraws the key. `enabledMMS`, SMS over IMS and the conference keys keep the conflict rule: Android reads them as true when they are missing, so a withdrawn key already leaves the feature on. Measured on 2026-10-10, this publishes 419 true switches in 280 profiles (VoLTE 147, Wi-Fi calling 100, video calling 172), 400 lines of `carrier-config-list.xml`, and keeps 12 withdrawn for the old single-source rule. `vonr_enabled_bool` is never published.
- Corroboration for generic APNs. A low-confidence generic APN row needs a second source or a primary maintained APN source. Otherwise the `uncorroborated_generic_apn` gate drops it.
- Samsung VoNR is a switch offer. Samsung's VoNR value comes only from the carrier pack token `+vonrcall`, which makes Samsung's Mobile networks screen offer the "VoNR (Voice over 5G)" switch for the carrier on that model. A Samsung `supported` therefore says the switch is offered there, not that VoNR is on by default or works in the field. Without the token VoNR stays `unknown`. Test and lab networks get no value, nor do private networks (MCC 999), a SIM that a KT phone dims the switch for, or a network that only Samsung's open-market US pack (XAA) offers it for, since that pack serves no operator. No CarrierConfig key is written from it, and `vonr_enabled_bool` is never published. The evidence index names the basis, sales codes and models in `capability_basis`. Samsung's IMS tables decide no VoNR: they list 5G for voice on almost every carrier, which networks that move calls to LTE need as well, so that lane gives none.
- Old single-source capabilities. A capability can rest on one independent source family whose newest upstream entry behind it is older than five years. Copies of one origin count once, as in the off rule: the LineageOS, Sony and Fairphone lists, the two Google lanes, Samsung's three lanes (OMC, IMS and CarrierConfig). Video calling, and every capability other than the four below, is then published as `unknown` for its age alone, with the gate `stale_single_source_entry:<capability>`. VoLTE, VoWiFi, MMS and Wi-Fi calling while roaming are published as `unknown` only on evidence besides the age, checked at the profile's own scope: `frozen_source_only:<capability>` when only a frozen copy gives the value (Sony's tree, frozen since 2020, or Fairphone's, whose pin has not moved since 2022), and `unseen_scope:<capability>` when no observation with an entry inside the five years, from any source family, covers the profile's scope. For an MVNO profile that is the same ICCID, GID or SPN value on one of its network codes, so a fresh observation of the host network does not cover it; for a plain profile it is a plain observation of one of its codes. Otherwise the old value is published, flagged `old_single_source`. A withheld label takes its switch with it: the capability-gating CarrierConfig key of the same feature is left out too, so `carrier-config-list.xml`, a `vendor.xml` applied on top of the ROM's own carrier configuration, keeps the ROM's value instead of switching on a feature the label withholds. A fresh source that contradicts it needs no gate of its own: a second family's different value already makes the capability `conditional`. An entry whose date is unknown never counts as old. APN rows and CarrierConfig values are not withheld for their own age; only the switch of a withheld capability goes with it.
- Rows LineageOS removed. A removal from LineageOS's list is one maintainer's decision, not a two-person review: a change merges with one maintainer's +2 and a Verified vote that is usually the author's own. Nor does it mean the APN is dead; most removals replace an old value or clean up. So each removal keeps its reason. When LineageOS removes an APN, the same row (network code, MVNO selector, APN, type set) is left out of every other source of the profile, unless an observation that gives it has an entry newer than the removal; then every copy stays. Two exceptions: a row moved to another code of the same country or another selector in the same commit is an edit, not a removal, and a removed extra network code is a retirement of that code, whose rows are left out only when no current Google CarrierSettings, Samsung or Apple observation lists the code. The evidence index records `lineageos_apn_removed:<commit>` with the number of rows left out, `<commit>` being the LineageOS commit first seen without them; `apn_removal_commits` gives each commit's date, Gerrit change and the reasons of its rows (`defunct`, `superseded`, `extra_code`, `moved`, `policy`, `vendor_rom_absent`, `unclassified`); and `withdrawn_profiles` lists a profile left with no fact. On 2026-10-06 that leaves out 73 rows in 34 profiles: 24 from a commit that cites a shutdown or merger, 16 replaced by newer values, 20 on extra Movistar Argentina codes, 7 that one maker's ROM no longer has and 6 old WAP APNs. It keeps 5 rows that Google's or Samsung's current data still ships and 2 on 722070, which Samsung and Apple still configure.
- No source-branded duplicates. A source name never becomes its own profile. Samsung and Apple observations for the same match set land in the same neutral profile.
- Samsung selectors are Samsung's own. A Samsung carrier-pack network publishes under each SIM rule its pack states (`omc.info` carrierList and the same rule in `customer.xml`): the network code alone, SPN, GID1, GID2, IMSI subset or ICCID prefix, all parts of a rule together. It never publishes under the name the pack shows in the network picker, which until the switch OCD wrote as an SPN; for 93.1% of the Samsung-only SPN profiles that could be checked, Samsung selects the network another way. A network gives no Samsung record when another network of the same pack has the same rule, because Samsung's SIM data does not tell them apart; when the rule is on MCC 001 or 999; when the rule cannot be written without widening it; or when the two files disagree. A plain rule also gives no Samsung record in two cases (round 13). On a code where a Samsung test network states a plain rule (310332, 311028, 311328 and 311390), no Samsung plain record publishes. And a plain rule a pack states for another country's code gives no record when that country's own packs name another network there, and either the network states plain rules in two or more countries in that pack or the pack belongs to another country and names no other network of that country: WOM's Colombian packs claim TELUS's 302220, Xplore's packs and Samsung's US pack claim Vodafone NL's 20404, and Tesco Mobile Ireland's pack claims Proximus's 20601. Without this, ordinary SIMs of those networks would have been sent to the other country's operator. There is no fallback to the network code alone: phones with such SIMs get what other sources give for their network code. A network reached through its network code alone names a profile only when no operator-facing name does, because a pack lists brands under their host's code. An observation stored before Samsung's rules were read is set aside as `samsung_selector_unproven` until it expires. This gate let the switch go only once at least 99% of the observations from packages Samsung still serves carried their rules (99.9% when an observation is matched to its package by firmware build); on the dry run of 2026-10-13 both were 100%. On that dry run 22,284 of 176,772 networks read (12.6%) gave no record: 20,570 share their rule with another such network of the pack, 1,405 are on MCC 999 or 001, and 309 have a rule OCD cannot write or that the files disagree on. 18,145 older observations were set aside, of which 17,888 would otherwise publish, and the profile count fell from 7,997 to 6,360, almost all of it Samsung-only profiles keyed by a network name (rule decisions of 2026-10-10, round 7, change 32; 2026-10-12, round 11; 2026-10-13, round 13). A profile without `samsung_omc` does not say Samsung has no settings for that network.
- Test and lab networks are quarantined, with the reason `test_or_lab_network` (`certification_test_profile` until 2026-10-05). One definition, `tools/lab_networks.py` in the private repo, serves this rule and Samsung's VoNR rule. An observation is left out when every network code it lists is a test code: MCC 001, or a code that a numbering authority reserves for testing or a carrier database names a test or lab network, with no source naming a commercial network on it (24407, 24099, 24681, 246081, 26209, 262800, 262830, 262840, 310014, 310028, 310322, 310886, 311400). The definition cites a source for each code. A broad record that also lists real codes keeps those. An observation is also left out when its display name or SPN is a test or lab name (`VZW TEST`, `Anritsu`, `Bell-lab`, `vodafone.de.lab`, `TMobile US LAB`, `Ericsson Test-SIM`), unless another observation of the same match set carries an operator name. A test-named entry on a real operator's code does not take the operator's profile out. A Samsung network reached through its network code alone does not count as an operator name here, as in naming. Names starting with GCF, PTCRB or Testbed and a Samsung `network_type_capability` starting with `GCF-` are always left out, as before. MCC 999 is a private network (ITU-T E.212 Appendix III), not a test network, and is published. On 2026-10-05 the rule removed 120 test and lab profiles and 426 APN rows. Since 2026-10-06 an observation is also left out, with the reason `unassigned_mcc`, when every network code it lists has an MCC that ITU-T E.212 does not assign: the list annexed to ITU Operational Bulletin No. 1117 with its later amendments (902, 991), plus 001 and 999. No SIM carries such an MCC, so nothing published under it can match. That removed 14 profiles: Google's default template 000000, Sony's "Virgin Mobile US" on 200053 (APN `0`) and "NRJ" on 20901, the overlays' 23302, 23304 and 254001 to 254006, and Samsung IMS profiles on 25851, 96654 and 96656. The validator refuses a profile whose every network code has such an MCC.
- IMSI selectors that a SIM can match. An IMSI starts with the SIM's MCC and MNC, and Android compares an IMSI pattern from the first digit and picks APN rows by the SIM's own network code, so a pattern that does not start with one of the profile's codes (`x` matching any digit) matches no SIM. Since 2026-10-10 an observation with such a pattern is quarantined, with the reason `imsi_selector_outside_network`, and an APN row whose own IMSI selector fits none of its codes is left out unless it carries a `carrier_id`. Leaving out only the pattern would widen the rows to every SIM of the network. That removed the two DIGI Spain profiles on 21405 and 22605, where Samsung's data gives DIGI's GID1 `44474553` as an IMSI (the DIGI Spain profile on 21422 with that GID1 stays), and 7 APN rows no SIM can match, among them an O2 IMS row with IMSI `2620739` in the plain 26208 profile. The validator refuses such a selector.
- Values Android defines. A CarrierConfig value outside the set Android defines for its key is left out of each observation before the merge, so it neither publishes nor conflicts with another source's value; no value is mapped to another. Today the set covers the two Wi-Fi calling mode keys, `carrier_default_wfc_ims_mode_int` and `carrier_default_wfc_ims_roaming_mode_int`: 0, 1 and 2 (`ImsMmTelManager.WIFI_MODE_*`). LineageOS device trees, most of them for Qualcomm phones, write 10, the "IMS preferred" mode of Qualcomm's IMS stack, which AOSP's Settings show as an unexpected mode and which a device that uses it keeps in its own `vendor.xml`. Since 2026-10-10 the 33 published values of 10 are gone, and 33 defined modes that other sources give publish where the 10 was the only disagreement, among them Google's mode 1 for Telekom Germany, Swisscom and 3 Austria. The validator refuses a value outside the set.

The evidence index lists `fact_sources` for every exported CarrierConfig value, APN fact and add-on whose sources are narrower than the profile's `sources`; a fact without an entry rests on all of them. A profile-wide source list is not proof for every field. Check the fact, not the profile. Capabilities have their own list, `capability_sources`: for every capability a source gives a value, the sources that turn it on and those that turn it off, whatever the profile publishes. So an `unknown` that one maker's off produced shows that maker, and a ROM can read which makers enable a feature.

`source_versions` names the exact origin behind each source family of a profile: a Pixel build ID, a Samsung firmware build, a Git commit, an Apple bundle and iOS version. To cite a fact, take the families `fact_sources` or `capability_sources` names for it, or all of `sources`, and read their versions. Where a family read several versions, the list holds all of them for the profile, not per fact.

## How the Android APN file is ordered

`generated/android/apns-conf.xml` is the file a phone loads, so its order is a decision, not a sort. Android 16 gives a SIM the rows of its scope, which is its network code and, when rows for its MVNO selector exist, that selector. It returns them in file order, and without a preferred APN it tries the first row that can serve a request first. [consume.md](consume.md) has the details. `tools/generate_android_outputs.py` therefore builds the file in nine steps.

1. It leaves out every row LineageOS's `apns-conf.xsd` rejects, such as an MMSC that is an address and port without a scheme, so the file passes the schema LineageOS builds with. `metadata.json` counts these rows as `omissions.apn_rows_rejected_by_lineageos_schema`. Two values the schema rejects only because they are written out, `authtype="-1"` and `skip_464xlat="-1"`, are TelephonyProvider's defaults, so the row leaves the attribute out and stays.
2. It collapses rows that Android treats as one APN. Two rows are one APN when they differ only in their label, in their type set, or in an attribute that repeats TelephonyProvider's default, such as `carrier_enabled="true"` or `protocol="IP"`. They become one row with the union of their types, which is what TelephonyProvider makes of them when it loads the file. Rows that differ only in username, password, auth type, MTU, server, label or bitmasks stay separate rows in the file, but they are one row to Android: step 8 writes the best-ranked of them last so its values win. Rows with another APN, proxy, port, MMS setting, protocol, MVNO selector or carrier id stay separate on the phone too.
3. It groups the rows by scope: network code, then MVNO selector, ignoring letter case as Android does for SPN and GID.
4. It takes the attach type off rows a current vendor does not back. Android attaches with the first row of the scope that serves `ia`, whatever the order of the internet rows. So when a current vendor gives a real APN for `default` or `ia` in the scope, every row whose APN value no current vendor gives for any type there loses `ia`, unless `ia` is its only type. The row stays with its other types, and the profile JSON keeps the type set its sources give; only `apns-conf.xml` changes. `metadata.json` counts these rows as `omissions.ia_types_left_out_not_vendor_current`. The current vendors are Google CarrierSettings and Samsung's two firmware lanes, because their lanes are checked against Google's update service and Samsung's firmware service, so what they give is what a current Pixel or Galaxy ships. Samsung's service also confirms the last build of a phone it stopped updating years ago, so a Samsung value counts only when it comes from a build at most three years old: for each APN fact the evidence index names, in `old_build_sources`, the Samsung sources whose every observation behind it comes from an older build. The limit was measured on 2026-10-06: against builds from July 2025 on, of the same match set, the full APN rows of builds up to June 2023 agreed 80 to 93 percent of the time, those of builds from July 2023 on 96 to 100 percent. A Samsung value also counts only when a phone's carrier pack gives it. A tablet's pack (models SM-X, SM-T and SM-P) configures a data-only device: on AT&T it gives `broadband`, `5gcbroadband` and `firstnet-broadband` where Samsung's phone packs give `nxtgenphone`, `nrphone` and `firstnet-phone`. So for each APN fact the evidence index names `samsung_omc` in `data_device_sources` when a tablet's pack gives it and no Samsung phone build at most three years old does; a value a current phone build gives too still counts. ## Why profiles are neutral

A profile says "the carrier tables behind this SIM configure these settings". It is a configuration, not a test result. It does not say "Samsung says this" or "Apple says this". One reason drives that choice.

A consumer needs one answer per SIM. A ROM cannot ask the user which vendor to believe.

The cost is real. When sources disagree, the consumer gets nothing for that key. The evidence index shows why, so a maintainer can go back to the sources.

## Device records next to the carrier value

For VoLTE, Wi-Fi calling, video calling and VoNR the one answer per SIM hides something. Android turns these features on only where the device and the carrier both allow them (ImsManager checks a device flag and the carrier's key), and phone makers set them per model. Most published `conditional` values for these four come from per-device files disagreeing: one LineageOS tree, one Pixel or one phone model turning a feature off that other devices' tables turn on (the counts are below). The per-carrier merge cannot fix that; it can only summarize it.

So since round 17 (rule decisions of 2026-10-17) the private pipeline also publishes `generated/devices/carrier-variants.json`, the device records. The step runs after the device catalog is built, reads the same observations the sanitizer's merge counts, through the same loader, and leaves out of the merge only the step that turns disagreeing sources into `conditional`: per device, the newest file decides (Google's current file over a frozen copy of the same Pixel, Samsung's newest Android major per model and sales code, a LineageOS file's last block), two files of one device that disagree give `conditional`, and a value whose newest entry is older than five years does not publish, for every capability (stricter than rule 7's evidence test for VoLTE and Wi-Fi calling). Only values a device's own file writes become records; Samsung's and Apple's offs never do. Every device value OCD publishes is listed, including those that agree with the carrier value. [data-model.md](data-model.md#device-records) lists the fields and rules.

Nothing else changes. The carrier value stays the family rule's summary and is never moved by a count of devices; `apns-conf.xml`, `carrier-config-list.xml`, `lookup.json`, the evidence index and the catalog files come out byte-identical with or without the step, and the file is not part of `data_digest`. APN rows, MMS and every CarrierConfig key stay per carrier: Android's APN file has no device key, MMS is a carrier service whose ends old device files do not show, and a per-device CarrierConfig value is not exported.

On 2026-10-17 the dry run gave 38,705 records with 265,394 device values for 789 devices (626 Samsung models and 163 catalog devices) on 3,945 profiles, 10.1 MB (246 KB gzip). Of the 522 published `conditional` values of the four capabilities, 246 have every device value `on`, 28 every one `off`, 230 a real split between devices, and 18 no device value at all.

Step 2 (round 17, round 8's deferred label change). Once the device records published, the summary for VoLTE, Wi-Fi calling and video calling stopped saying `conditional` where the only off is one non-operator family's per-device files and each of those offs is an `off` device record: the value is `supported`, `capability_sources` keeps the off, and the gate `single_family_off:<capability>` names it. The on must publish standing alone under the five-year rule. An off the device file does not show, because it is older than five years, binds to no single device, is carrier-wide, or meets the same device's other overlay layer, keeps `conditional`. MMS, VoNR, conference calling and the other capabilities are not touched, and neither are CarrierConfig or APN rows. ## Why an MVNO can land in its host's profile

Grouping by exact match set has one visible consequence. An MVNO that no source distinguishes from its host network merges into the host's profile.

LIDL Connect runs on the Vodafone Germany network, `26202`. No source names it with an SPN, GID, or IMSI prefix. So no profile names it. A LIDL Connect SIM resolves the plain `26202` profile plus whichever `26202` SPN profile matches the SPN on the SIM. The result is Vodafone's data, which may or may not be right for that MVNO.

The limit exists because the sanitizer only publishes what a source observed. It does not invent a selector. A maintained source that publishes a tested SPN or GID prefix, or an importer/mapping change, is the way to add one.

## What the 180-day window measures

Every source snapshot carries two dates. `revision_date` says when the upstream revision was published. `checked_at` says when automation last fetched the source with success: it is the last successful sync of that lane, a liveness date. It does not say that the values inside are still right. An unchanged source keeps passing as long as its lane runs, and an APN row last changed in 2010 passes with it.

The private sanitizer quarantines an observation when its source's `checked_at` or its own review date is 180 days old or more; observations carry no `checked_at` of their own. Vendor observations must also name how their freshness was proven, and only two lanes actually ask the vendor whether a setting is current: Samsung, whose firmware build Samsung's update service must confirm as current, and the GrapheneOS Pixel lane, which checks every Pixel against Google's live update service. Other vendor data, such as the Pixel vendor files from LineageOS's `TheMuppets` mirrors, passes as a versioned artifact at any age.

The public side publishes the result as a window. `checks_through` is the oldest `checked_at` and review date among the observations that survived quarantine. `stale_after` is `checks_through` plus 180 days, a lane-liveness deadline. Both sit in `generated/android/metadata.json`, in the header of the XML files and per profile in `generated/android/lookup.json`. `tools/generate_android_outputs.py` copies them from `generated/evidence-index.json` when the sanitizer publishes them there and computes them otherwise. `tools/validate_public_carrier_data.py` checks that the pair agrees with every snapshot date, then compares the UTC date with `stale_after`; it trusts the published `stale_after` and does not re-check each `checked_at` against 180 days. `tools/validate_device_catalog.py` does the same with `generated_from_checks_through` plus 180 days.

Stale is worse than missing. A missing APN row makes a phone fall back to its own defaults or ask the user. A stale row looks authoritative and sends the phone to a dead MMSC. Nobody notices until messages fail. So the project drops what a dead lane last said, drops rows LineageOS removed unless a newer source still gives them, and publishes how old the rest is (next section).

`checks_through` is the oldest of the snapshot checks and the observation review dates. The snapshot records are re-checked weekly, so the oldest Samsung observation sets it: an observation from a superseded firmware build keeps its July 2026 date until a daily Samsung run re-extracts it, and what is still from 2026-07-14 on 2027-01-10 is quarantined then. Because the limit counts the day it is reached, `stale_after` is the day that day's publish sets the oldest observation aside, so the 04:17 UTC alarm never sees a snapshot past `stale_after` while that day's publish was still to come. Past `stale_after` the validators warn by default and exit 0, so a clone keeps validating. The daily public job passes `--freshness fail`, and `--liveness fail`, which fails when one lane's source was not checked within its limit (10 days for the daily Samsung lanes `samsung_omc` and `samsung_ims`, 21 days for every weekly lane) or the last publish is more than 21 days old; a failure opens an issue labeled `stale-data`. Run this command to see the window:

```bash
python3 -c 'print(*[__import__("json").load(open("generated/android/metadata.json"))[k] for k in ("checks_through", "stale_after")])'
```

## How old the entries behind a fact are

A check date says when automation last confirmed a source. It does not say how old the entries inside that source are. A source checked last week can still carry an APN row last changed in 2010.

So each observation also records the date of the newest upstream entry behind it. An entry is one APN row, one provider block, one CarrierConfig file or block, one Pixel carrier file, one Apple bundle, or one Samsung CSC package. The git-based lanes use the first day they saw the entry's current content, seeded from git history. Apple uses the publish date in the bundle's download URL from Apple's index. Samsung uses the build month in the CSC build string of the package the observation was read from (the one its firmware build names; without a build, the newest package of its model and CSC family). Every date is the latest possible one, so an age read from it is a minimum. When no date can be found, none is published.

The evidence index publishes the result to the month. `newest_entry` is the newest entry behind a profile, and `generated/android/lookup.json` repeats it per profile. `capability_newest_entries` gives it for each capability a source gives a value, also one a gate publishes as `unknown`. Both appear only where every supporting observation is dated. `flags` marks a capability whose value rests on one family with an entry over five years old as `old_single_source`; flags withhold nothing. Until 2026-10-06 a second flag, `capability_label_withheld`, marked a capability-gating CarrierConfig key published next to a withheld label; such a key is now left out. On 2026-10-04, 1,009 of 7,806 profiles have no entry newer than September 2021, more than five years old; 645 of them rest on Apple bundles alone and 129 on AOSP alone, and 711 of them put 1,056 APN rows into `apns-conf.xml`. Run this command to print the oldest dated capabilities, published or withheld:

```bash
python3 -c 'import json; e=json.load(open("generated/evidence-index.json")); print(*sorted((d, k, p["profile_id"]) for p in e["profiles"] for k, d in p.get("capability_newest_entries", {}).items())[:10], sep="\n")'
```

How to read the age of a value: it is older when every source behind it is a frozen copy (TheMuppets' Pixel trees, Sony's tree, Fairphone's tree), an old build (`old_build_sources`) or a superseded Samsung pack (`superseded_pack_sources`). `capability_sources`, `fact_sources` and `sources` name the sources behind each value, and `capability_newest_entries` and `newest_entry` give the month. There is no separate age flag: a date records the last change of an entry, not a confirmation that it is still right.

Old is not always wrong, and age is a gradual signal, not a five-year step. A review on 2026-10-05 compared old "supported" capabilities with fresh data from another source family. They agreed on VoLTE 94.4 percent of the time (0.5 percent contradicted), VoWiFi 86.3 (0.8), video calling 91.5 (5.2) and MMS 95.4 (4.2). Disagreement grows with age, from claims under one year old to claims over five (VoLTE 2.7 to 6.7 percent, VoWiFi 6.2 to 16.9, video calling 5.6 to 10.6, MMS 1.0 to 3.6), but most of the rise happens before three years: claims over five years old agree about as often as claims three to five years old. So the five-year limit is a cut on a slope, and since 2026-10-06 age alone withholds only video calling, of whose 82 old single-source values fresh data contradicted 8 and confirmed 1. An old single-source VoLTE, VoWiFi, MMS or Wi-Fi calling while roaming value is withheld only when its one source is a frozen copy or no fresh observation covers the profile's scope, as described above. On 2026-10-06 that withholds 714 values instead of 895: 82 video calling values for their age, 46 values only Sony's frozen tree gives, and 586 that no fresh observation covers, most of them in SIM-specific profiles that only an old Apple bundle, LineageOS device overlay or AOSP list describes. 181 values that age alone had withheld are published as `supported` again. A withheld capability is published as `unknown`, keeps its date, and is flagged `old_single_source`. Since 2026-10-06 the CarrierConfig key that switches the same feature on is left out with it: the label and the switch say the same thing, and a ROM that applies `carrier-config-list.xml` keeps its own value for the key. That left out 486 keys, 127 of them in `carrier-config-list.xml` (`carrier_vt_available_bool` 45, `carrier_wfc_ims_available_bool` 34, `carrier_volte_available_bool` 32, `enabledMMS` 16), and withdrew 2 profiles whose last facts they were. APN rows and CarrierConfig values only show their age. That is not because they agreed more often: in the study of 2026-10-03 CarrierConfig values agreed 76 percent of the time, less than VoWiFi (88) and video calling (80) on that study's measure.

## What the public repo checks

The workflow `Validate carrier data` in `.github/workflows/validate.yml` has two jobs. `validate` runs on push to `main`, on pull requests, and on manual dispatch. It validates the profiles against the stable index and the device catalog in warn mode, runs the test scripts, and regenerates `generated/android/` to confirm nothing drifted. Then it checks `generated/android/apns-conf.xml` with `xmllint` against LineageOS's `apns-conf.xsd`. `tools/lineageos/apns-conf.xsd` is a byte copy of that schema at LineageOS `android_vendor_apn` revision `6e73ba90`, Apache-2.0 like the rest of the tools. `tools/validate_carrier_variants.py` checks the device records ([data-model.md](data-model.md#device-records)), and passes when the file is absent. It is the required check on `main`. Pull requests, including carrier-data ones, are untrusted input: they run through the `pull_request` trigger with a read-only token (`permissions: contents: read`), and the workflow uses no secrets. `freshness-alarm` runs daily at 04:17 UTC by cron and on manual dispatch. It runs the validators with `--freshness fail`, and the carrier validator also with `--liveness fail`: that fails when any lane's `checked_at` in `source_snapshots` is older than that lane's limit, or the last commit titled `Update sanitized carrier data` on the validated branch is more than 21 days old. The limit is 10 days for the two Samsung lanes, `samsung_omc` and `samsung_ims`, which run daily on the self-hosted runner and whose manifest can lag up to six days (`LANE_LIVENESS_MAX_AGE_DAYS`), and 21 days for every other lane (`LIVENESS_MAX_AGE_DAYS` in `tools/validate_public_carrier_data.py`). Every weekly import re-checks its sources and every check reaches this repo through a publish, so 21 days means three missed weekly runs; `stale_after` alone would notice a stopped pipeline only about six months later. Each lane is checked on its own, so one dead lane shows even while the others keep publishing. While a Samsung build publishes under the vendor build grace (`vendor_build_grace` in the evidence index: a new build of the tracked firmware appeared and the IMS and CarrierConfig indexes were not yet rebuilt from it, so the previous build's values keep publishing for up to 30 days), the liveness check warns every day and the job shows the warning on the run; once the build's last confirmation is more than 10 days old it fails like a stopped Samsung lane, which leaves about 19 days to fix the refresh before the values drop. For a deliberate pause, the repository variable `LIVENESS_SNOOZE_UNTIL` (a date) turns the liveness failure into a warning up to that day. When the validators fail it opens one issue labeled `stale-data` with the validator output, and it does not open a second while one is open. When they pass again it closes that issue. It is the only job with `issues: write`, and it never runs on a pull request. The dispatch input `simulate_today` passes `--today` to the validators, so the alarm can be rehearsed before the real date arrives. GitHub disables a public repository's scheduled workflows after 60 days without a commit and emails the owner first. Every data publish is a commit to `main`, so the alarm keeps running while publishes land, and `gh workflow enable validate.yml` turns it back on after a pause.

The `validate` job also runs a phone-level guard, `tools/check_phone_guard.py`, on every pull request whose `apns-conf.xml` differs from its base (rule decisions of 2026-10-06, publish guard of 2026-10-08). It reads the base's and the head's file with `tools/android_phone_model.py`, a model of what an Android phone makes of the file: TelephonyProvider's merge of equal rows, ApnSetting and DataProfileManager's dedupe, read from the LineageOS sources. For every scope in both files and every 3GPP data network type (GPRS, EDGE, UMTS, HSPA, HSPA+, LTE and NR) it holds four changes: the scope loses its internet lead, loses its attach lead, loses working MMS (a route with an MMSC), or MMS moves from a current vendor's tuple (APN, MMSC, MMS proxy, MMS port, from the generator's own records of the head) to one no current vendor gives; APN names and MMSCs are compared case-folded, and a trailing `/` on the MMSC is ignored. Everything else it only reports: credentials and HTTP proxies on the leads, a lead moving to an APN no current vendor gives, scopes that leave the file, losses only on Wi-Fi (IWLAN) or CDMA types, other MMS moves, stored-row counts and `persist_apns_for_plmn` events. It also reports a lead that stops sending credentials it sent before (a username or password with a resolved auth type other than 0), with a `WARNING:` line when every row a current vendor backs for the new lead's APN in the scope carries credentials (rule decisions of 2026-10-13, round 14). A hold fails `validate`, so the pull request cannot merge. It prints each trip with its network types and old and new values, then a digest: the first 16 hex characters of sha256 over the sorted trip lines. The trips pass only when the pull request body has the exact line `phone-guard-accept: DIGEST` for them; `validate` also runs when the body is edited, so adding the line checks again. Any other or changed trip changes the digest, and there is no other bypass. A data publish that trips is opened as a draft labeled `publish-held` and stays unmerged until later data or a generator fix removes the trip, or the private publish workflow is dispatched with that digest; the data already on `main` stays live meanwhile, and nothing releases on a timer.

Two more reports sit next to the guard and never hold anything (rule decisions of 2026-10-18, round 20). The guard reports the `ims` and `emergency` leads of every scope in both files on the 7 hold types and IWLAN. For `ims` it reports the lead lost, its APN changed (case-folded), or only its protocol or roaming protocol changed, with the old and new values and the network types; the `ims` lead is the first data profile that serves the type, as the phone model picks the internet lead, and a scope that gains an `ims` lead is not reported. The `emergency` lead is the one the phone uses (rule decisions of 2026-10-18, round 21): the first profile that can handle `emergency` (enabled and typed `emergency`; an empty type has no emergency bit), serves the network type, has cellular infrastructure and passes Android's APN set filter (set -1 or the preferred set, taken as 0). When no profile of the scope can handle `emergency` on any network type, Android adds its own default profile, APN `sos` with `IPV4V6` at home and when roaming and APN set -1 (`DataProfileManager`), and the guard does the same. So it prints an emergency lead "gained" (Android's default to a row of the file), "lost" (a row of the file to Android's default) or "changed" (any other change of what the request carries: APN, either protocol, auth type, credentials, MTU, network types, `skip_464xlat`, `always_on`, profile ID or modem-cognitive), and labels each value against Android's default: `equal`, `carrier name` (an APN other than `sos`), `IPv4 only`, `IPv6 only`, `request attribute`, or `network-type gap` for a network type left without an emergency profile, which Android does not fill because its default comes only when no network type has one. It also prints "emergency profile missing under APN set N" for a scope where a preferred APN set N (0, or the set of a row that serves `default`) leaves no emergency profile in the head but did not in the base. Lines that touch LTE, NR or IWLAN come first in each list. An unset protocol counts as `IP`, as TelephonyProvider stores it. It also reports an APN named like an emergency APN (`sos`, a name containing `emergency`, or one starting with `e911`) that becomes the internet or attach lead. These lines never enter the trips or the digest, and `--report-json` keeps every one under `watch`. On a pull request that changes `generated/android/carrier-config-list.xml`, `tools/diff_carrier_config.py` compares the base's file with the head's, block by block (keyed by the filter attributes, not `name`), and writes to the step summary: every added, removed or changed line of the safety class (key names with `emergency`, `e911` or `ecbm`, the WPS, TTY and RTT keys, and `iwlan.*`) in full, and the other keys as counts per key. That step never fails the job.
