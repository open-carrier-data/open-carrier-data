# How the data is built

This page explains where a carrier profile comes from and why it looks the way it does. It is not a command reference. For commands, read [consume.md](consume.md).

## The pipeline in one picture

Every value in `carriers/open/` passes through the same five stages:

```text
source families          upstream repos, vendor indexes, firmware baselines
      |
candidate observations   private normalized records, one per source and carrier match
      |
the sanitizer            merges, quarantines, and strips private material
      |
carrier profiles         neutral JSON in carriers/open/, one file per match set
      |
generated files          generated/index.json, evidence-index.json, android/, devices/
```

The first three stages live in the private repo. Since 2026-09-24 a weekly GitHub-hosted job runs them for every source family except Samsung, whose lane needs firmware downloads and pinned image tools that only a self-hosted runner has. Since the same day that runner is back on the owner's machine as a user service, and the Samsung lane runs daily at 02:00 UTC in one bounded unit: up to 2,048 firmware update server probes and 50 selective CSC extractions, then a date refresh of every observation whose firmware build was confirmed current. The public repo receives carrier profiles and generated files, then its own workflow validates them. The public tools can regenerate `generated/android/` from the profiles, but they cannot rebuild profiles from sources.

## Sources become candidate observations

A source family is one upstream. Examples are the LineageOS APN repo, Apple's carrier bundle index, or a Samsung firmware baseline. An importer reads the upstream and writes candidate observations. Each observation records one carrier match set, the facts seen, the source family, the upstream revision, the date automation checked it, and, where it can be found, the date of the newest upstream entry behind it. Raw source material stays in the private repo.

Samsung's IMS and CarrierConfig values come from one build of the newest One UI branch; the older branch differs mostly in entries Samsung later removed or reworked.

[SOURCES.md](../SOURCES.md) lists every source family and its terms.

## The sanitizer merges observations into profiles

The sanitizer groups observations and applies fixed rules. The rules are:

- Grouping by exact match set. Observations with the same `mccmnc`, `spn`, `gid1_prefixes`, `gid2_prefixes`, `iccid_prefixes`, `imsi_prefix_patterns`, and `android_carrier_ids` form one profile. A different match set forms a different profile. The `spn` comparison ignores letter case, so `TELEKOM` and `Telekom` land in one profile. The profile keeps the spelling the most independent source families give, then the one from the higher naming authority (the order below), then the first in character order; observation counts play no part, so a profile ID does not change when a firmware run adds or expires observations.
- Naming. A display name never changes a profile: `profile_id` is a hash of the match set alone. Names are ranked in three steps, with words like `internet` or `mms` stripped before they are compared. First the kind of source: any operator-facing name (AOSP's carrier list, Google CarrierSettings, Apple's bundles, GNOME's provider list, the AOSP-derived APN lists, Samsung's OMC carrier packs) beats Samsung's IMS profile names, which are internal labels such as `GenericIR92 US CSpire` or `Dish US`. A label is used only when nothing else names the match set. Then the number of distinct source families behind the name: the two Google lanes count as one, and so do the LineageOS, Sony and Fairphone APN lists, which copy AOSP's list. Observations are not counted, so duplicate firmware builds, models or Pixel devices cannot win a tie. Equal support falls to a fixed order of naming authorities: Apple's bundle names, Samsung's OMC network names, AOSP's carrier list, Samsung's carrier table, GNOME's provider list, the APN-list labels, and last Google's canonical identifiers such as `tmobile_us`. Before any ranking, candidates that name no carrier are left out: an empty name; "Carrier", "Default", "Unknown" or "Generic", alone or with a number; Google's private-network template `pn_xx` (1,099 MCC 999 profiles, now `Carrier 999xx`); an importer's fallback such as `LineageOS 26202`; a name with `=`, such as Google's selector identifiers `26201Spn=Debitel` or `310410Gid1=60Ff`; a network code alone, also with a country code (`26203`, `26214 De`); and a bare APN label such as `Internet`. Only a profile with no candidate left gets the neutral `Carrier <mccmnc>`. The winning name is then published in its cleanest spelling among the candidates that are the same name apart from case, punctuation, APN words or a trailing country code: without an APN word, without a country code, not all lower case, without underscores, then by naming authority. So `o2-de`, `o2 - de` and `O2 De` become `O2` where a source writes `O2`, and `O2 De` where none does. Every published spelling is one a source gives. Spellings of one name do not add to its support. Entry dates do not choose a name: they date the settings around a name, not the name, so they cannot tell a retired brand such as `E-Plus` from a name whose settings have not changed.
- Agreement. When every source that names a fact gives the same value, the value is published. An off for a capability, or a false capability switch in CarrierConfig, also needs the evidence described below.
- Conflict omission. When sources give different values for one CarrierConfig key or one add-on key, the value is left out. The evidence index records the conflict with `resolution: omitted_from_stable`. Two keys are compared as sets, because Android reads them into a set: `carrier_metered_apn_types_strings` and `carrier_metered_roaming_apn_types_strings`. The same APN types in another order are not a conflict, and the value keeps the order of the first source that gives it.
- APN variants. When sources disagree on one APN selector, every variant is published, because an APN list holds several rows per type by design. The evidence index records the conflict with `resolution: published_variants`. Rows that differ in proxy, port, username or password are separate rows, a missing value meaning none, and a source backs a row only when it gives the same four values: one source's proxy or credentials are never filled into another source's row. For a row's `mms` type the MMS proxy and, with an MMS proxy, the MMS port count too, because the MMS service sends through them: a source backs an MMS row only when it gives the same MMS proxy and port. An MMS port without an MMS proxy does not count, and for other types the MMS settings merge as before. Other attributes, such as the protocol or the MMSC, still merge into one row when the sources do not disagree. A profile lists its rows by APN. The Android files order them by the evidence behind each row, see [How the Android APN file is ordered](#how-the-android-apn-file-is-ordered).
- Usable APN values. The sanitizer removes control characters and surrounding whitespace from every APN string, SPN and display name, so Google's SPN `C Spire\r` is the same profile as `C Spire`. An MMSC without a scheme gets `http://`, because Android's MMS service opens it as a URL, and `http:/host`, `http//host` or a space after the scheme are repaired. `null`, `none` and a bare `http://` mean no MMSC. A `*` type means what Android reads from it, `ApnSetting.TYPE_ALL`: `default`, `hipri`, `mms`, `supl`, `dun`, `fota`, `ims` and `cbs`. The validator refuses a profile that breaks any of these rules.
- MMS rows need an MMSC. Android's MMS service looks the MMSC up among the SIM's `mms` rows with the APN its MMS connection uses. So a row typed `mms` without an MMSC keeps the type only when another `mms` row of the same APN and MVNO selector carries one. Otherwise it loses `mms`, and a row that served only MMS is dropped. The evidence index records the `mms_without_mmsc` gate. The validator refuses an `mms` row whose APN has no MMSC in its profile.
- Empty APNs are not published. An `ia` row with an empty APN asks the network to pick the APN, and no source says why its rows are empty; an empty APN on any other row cannot work. Every importer drops such a row. [consume.md](consume.md#rows-with-an-empty-apn) says what Android does instead.
- Empty profiles are dropped. A profile left with no APN, no CarrierConfig, no add-on, and no known capability is not written. The sanitization report counts these as `empty_profile_count`.
- Conditional capabilities. Capabilities are the one exception. A disagreement becomes `conditional` instead of an omission.
- Google's current file supersedes its frozen copies. Google's file for a Pixel it no longer updates (Pixel 1 to 5a), or an older snapshot of a current Pixel's file, read from TheMuppets' frozen Pixel trees (`google_pixel_vendor_carriersettings`), is a superseded revision of Google's carrier settings. It counts for a capability or a CarrierConfig key only where Google's current file (`google_carriersettings`) gives no value; where the current file gives one, the frozen copies are left out for that key before any other rule. A conflict they alone caused is recorded with `resolution: superseded_device_file`, and `capability_sources` and `capability_newest_entries` follow the published value. This is the same reason Samsung's IMS table is read from the newest One UI branch only and the APN ordering puts a current vendor's row first. Measured on 2026-10-09, another family agreed with the current Google value in 223 of 223 capabilities and 343 of 343 CarrierConfig values this settles, and with the frozen value in none. About one in five of those capabilities was Google keeping a feature off on an old Pixel, which gets no more updates. Disagreements between current devices, between device trees, between a frozen tree of another maker and LineageOS, and between families are not settled by dates: they stay `conditional`, or the CarrierConfig value stays left out.
- One maker's off is not proof. A maker's or maintainer's carrier table that turns a feature off says how their phones are set up, not that the carrier lacks the feature. So a capability is `unsupported` only when the operator's own configuration turns it off, or at least two independent source families turn it off and none turns it on. An off from one family alone is published as `unknown`, and the evidence index records the gate `single_family_off:<capability>`. The LineageOS, Sony and Fairphone APN lists count as one family, as do the two Google lanes and Samsung's three lanes (OMC, IMS and CarrierConfig), the same grouping the APN ordering uses. Samsung's and Apple's offs never count. Both write an off almost always as a missing entry: 3,622 of 3,674 offs in Samsung's tracked IMS table, and most iPhone bundles. Their written offs describe phones or defaults, not the carrier: measured on 2026-10-09, Samsung's written table offs agreed with another family's off in 2 of 9 comparable cases, Samsung's phone-pack offs in 0 of 31, and Apple's written falses in 0 of 12. A carrier pack's off, including a carrier-branded pack's off for its own SIMs, describes the phones that use the pack; it is not published. On 2026-10-06 that kept VoWiFi `supported` on the 16 Spectrum and Xfinity profiles whose branded Galaxy packs switch it off on some models.
- The operator's own configuration. A carrier pack, branded or not, is maker configuration. Two kinds of source count on their own, and only where it was checked: Google's CarrierSettings for its own Google Fi service (Google's carrier names `fi_us`, `fi_tmo_us`, `fi_extended_us`, `fi_at` and `fi_es`), and an AOSP CarrierConfig file whose git history shows the carrier wrote it. On 2026-10-04 that is one file, SETAR's (carrier ID 493, Aruba): both commits that wrote it are by SETAR staff. The other AOSP offs were written by Google staff and count like any other source.
- An ended service stays as the tables say. When an operator ends a service, phone makers' tables often keep it for months or years: on 2026-10-09 Google's current file and all current Samsung observations of their base profiles still configured MMS for Telekom, O2 and 1&1 Germany, which ended it on 30 June 2026. OCD publishes what the tables configure and does not track service status, so such a value stays `supported` and its APN rows stay; on Android a missing MMS row does not make MMS work, it only changes how a send fails.
- Capability switches in CarrierConfig. A false value of a key that switches a capability off on the phone is left out when one non-operator family alone sets it, so a ROM that applies the profile does not switch the feature off on that family's word. The evidence index records the gate `single_family_off:<key>`. The keys are `carrier_volte_available_bool`, `carrier_wfc_ims_available_bool`, `carrier_vt_available_bool`, `enabledMMS`, `imssms.sms_over_ims_supported_bool`, `support_ims_conference_call_bool` and `support_conference_call_bool`. No other key is affected, and true values stay. `vonr_enabled_bool` is never published.
- Corroboration for generic APNs. A low-confidence generic APN row needs a second source or a primary maintained APN source. Otherwise the `uncorroborated_generic_apn` gate drops it.
- Samsung VoNR is a switch offer. Samsung's VoNR value comes only from the carrier pack token `+vonrcall`, which makes Samsung's Mobile networks screen offer the "VoNR (Voice over 5G)" switch for the carrier on that model. A Samsung `supported` therefore says the switch is offered there, not that VoNR is on by default or works in the field. Without the token VoNR stays `unknown`. Test and lab networks get no value, nor do private networks (MCC 999), a SIM that a KT phone dims the switch for, or a network that only Samsung's open-market US pack (XAA) offers it for, since that pack serves no operator. No CarrierConfig key is written from it, and `vonr_enabled_bool` is never published. The evidence index names the basis, sales codes and models in `capability_basis`. Samsung's IMS tables decide no VoNR: they list 5G for voice on almost every carrier, which networks that move calls to LTE need as well, so that lane gives none.
- Old single-source capabilities. A capability can rest on one independent source family whose newest upstream entry behind it is older than five years. Copies of one origin count once, as in the off rule: the LineageOS, Sony and Fairphone lists, the two Google lanes, Samsung's three lanes (OMC, IMS and CarrierConfig). Video calling, and every capability other than the four below, is then published as `unknown` for its age alone, with the gate `stale_single_source_entry:<capability>`. VoLTE, VoWiFi, MMS and Wi-Fi calling while roaming are published as `unknown` only on evidence besides the age, checked at the profile's own scope: `frozen_source_only:<capability>` when only a frozen copy gives the value (Sony's tree, frozen since 2020, or Fairphone's, whose pin has not moved since 2022), and `unseen_scope:<capability>` when no observation with an entry inside the five years, from any source family, covers the profile's scope. For an MVNO profile that is the same ICCID, GID or SPN value on one of its network codes, so a fresh observation of the host network does not cover it; for a plain profile it is a plain observation of one of its codes. Otherwise the old value is published, flagged `old_single_source`. A withheld label takes its switch with it: the capability-gating CarrierConfig key of the same feature is left out too, so `carrier-config-list.xml`, a `vendor.xml` applied on top of the ROM's own carrier configuration, keeps the ROM's value instead of switching on a feature the label withholds. A fresh source that contradicts it needs no gate of its own: a second family's different value already makes the capability `conditional`. An entry whose date is unknown never counts as old. APN rows and CarrierConfig values are not withheld for their own age; only the switch of a withheld capability goes with it.
- Rows LineageOS removed. A removal from LineageOS's list is one maintainer's decision, not a two-person review: a change merges with one maintainer's +2 and a Verified vote that is usually the author's own. Nor does it mean the APN is dead; most removals replace an old value or clean up. So each removal keeps its reason. When LineageOS removes an APN, the same row (network code, MVNO selector, APN, type set) is left out of every other source of the profile, unless an observation that gives it has an entry newer than the removal; then every copy stays. Two exceptions: a row moved to another code of the same country or another selector in the same commit is an edit, not a removal, and a removed extra network code is a retirement of that code, whose rows are left out only when no current Google CarrierSettings, Samsung or Apple observation lists the code. The evidence index records `lineageos_apn_removed:<commit>` with the number of rows left out, `<commit>` being the LineageOS commit first seen without them; `apn_removal_commits` gives each commit's date, Gerrit change and the reasons of its rows (`defunct`, `superseded`, `extra_code`, `moved`, `policy`, `vendor_rom_absent`, `unclassified`); and `withdrawn_profiles` lists a profile left with no fact. On 2026-10-06 that leaves out 73 rows in 34 profiles: 24 from a commit that cites a shutdown or merger, 16 replaced by newer values, 20 on extra Movistar Argentina codes, 7 that one maker's ROM no longer has and 6 old WAP APNs. It keeps 5 rows that Google's or Samsung's current data still ships and 2 on 722070, which Samsung and Apple still configure.
- No source-branded duplicates. A source name never becomes its own profile. Samsung and Apple observations for the same match set land in the same neutral profile.
- Test and lab networks are quarantined, with the reason `test_or_lab_network` (`certification_test_profile` until 2026-10-05). One definition, `tools/lab_networks.py` in the private repo, serves this rule and Samsung's VoNR rule. An observation is left out when every network code it lists is a test code: MCC 001, or a code that a numbering authority reserves for testing or a carrier database names a test or lab network, with no source naming a commercial network on it (24407, 24099, 24681, 246081, 26209, 262800, 262830, 262840, 310014, 310028, 310322, 310886, 311400). The definition cites a source for each code. A broad record that also lists real codes keeps those. An observation is also left out when its display name or SPN is a test or lab name (`VZW TEST`, `Anritsu`, `Bell-lab`, `vodafone.de.lab`, `TMobile US LAB`, `Ericsson Test-SIM`), unless another observation of the same match set carries an operator name. A test-named entry on a real operator's code does not take the operator's profile out. Names starting with GCF, PTCRB or Testbed and a Samsung `network_type_capability` starting with `GCF-` are always left out, as before. MCC 999 is a private network (ITU-T E.212 Appendix III), not a test network, and is published. On 2026-10-05 the rule removed 120 test and lab profiles and 426 APN rows. Since 2026-10-06 an observation is also left out, with the reason `unassigned_mcc`, when every network code it lists has an MCC that ITU-T E.212 does not assign: the list annexed to ITU Operational Bulletin No. 1117 with its later amendments (902, 991), plus 001 and 999. No SIM carries such an MCC, so nothing published under it can match. That removed 14 profiles: Google's default template 000000, Sony's "Virgin Mobile US" on 200053 (APN `0`) and "NRJ" on 20901, the overlays' 23302, 23304 and 254001 to 254006, and Samsung IMS profiles on 25851, 96654 and 96656. The validator refuses a profile whose every network code has such an MCC.

The evidence index lists `fact_sources` for every exported CarrierConfig value, APN fact and add-on whose sources are narrower than the profile's `sources`; a fact without an entry rests on all of them. A profile-wide source list is not proof for every field. Check the fact, not the profile. Capabilities have their own list, `capability_sources`: for every capability a source gives a value, the sources that turn it on and those that turn it off, whatever the profile publishes. So an `unknown` that one maker's off produced shows that maker, and a ROM can read which makers enable a feature.

`source_versions` names the exact origin behind each source family of a profile: a Pixel build ID, a Samsung firmware build, a Git commit, an Apple bundle and iOS version. To cite a fact, take the families `fact_sources` or `capability_sources` names for it, or all of `sources`, and read their versions. Where a family read several versions, the list holds all of them for the profile, not per fact.

## How the Android APN file is ordered

`generated/android/apns-conf.xml` is the file a phone loads, so its order is a decision, not a sort. Android 16 gives a SIM the rows of its scope, which is its network code and, when rows for its MVNO selector exist, that selector. It returns them in file order, and without a preferred APN it tries the first row that can serve a request first. [consume.md](consume.md) has the details. `tools/generate_android_outputs.py` therefore builds the file in six steps.

1. It leaves out every row LineageOS's `apns-conf.xsd` rejects, such as an MMSC that is an address and port without a scheme, so the file passes the schema LineageOS builds with. `metadata.json` counts these rows as `omissions.apn_rows_rejected_by_lineageos_schema`. Two values the schema rejects only because they are written out, `authtype="-1"` and `skip_464xlat="-1"`, are TelephonyProvider's defaults, so the row leaves the attribute out and stays.
2. It collapses rows that Android treats as one APN. Two rows are one APN when they differ only in their label, in their type set, or in an attribute that repeats TelephonyProvider's default, such as `carrier_enabled="true"` or `protocol="IP"`. They become one row with the union of their types, which is what TelephonyProvider makes of them when it loads the file. Rows that differ only in username, password, auth type, MTU, server, label or bitmasks stay separate rows in the file, but they are one row to Android: step 6 writes the best-ranked of them last so its values win. Rows with another APN, proxy, port, MMS setting, protocol, MVNO selector or carrier id stay separate on the phone too.
3. It groups the rows by scope: network code, then MVNO selector, ignoring letter case as Android does for SPN and GID.
4. It takes the attach type off rows a current vendor does not back. Android attaches with the first row of the scope that serves `ia`, whatever the order of the internet rows. So when a current vendor gives a real APN for `default` or `ia` in the scope, every row whose APN value no current vendor gives for any type there loses `ia`, unless `ia` is its only type. The row stays with its other types, and the profile JSON keeps the type set its sources give; only `apns-conf.xml` changes. `metadata.json` counts these rows as `omissions.ia_types_left_out_not_vendor_current`. The current vendors are Google CarrierSettings and Samsung's two firmware lanes, because their lanes are checked against Google's update service and Samsung's firmware service, so what they give is what a current Pixel or Galaxy ships. Samsung's service also confirms the last build of a phone it stopped updating years ago, so a Samsung value counts only when it comes from a build at most three years old: for each APN fact the evidence index names, in `old_build_sources`, the Samsung sources whose every observation behind it comes from an older build. The limit was measured on 2026-10-06: against builds from July 2025 on, of the same match set, the full APN rows of builds up to June 2023 agreed 80 to 93 percent of the time, those of builds from July 2023 on 96 to 100 percent. Google's update service likewise confirms its shared `others` file as a whole, not each entry: in two years 5 of its 688 entries changed and 119 were removed, and against Samsung builds of three years or less in the same scope its values agreed 83 percent (default) and 79 percent (MMS), where Google's per-carrier files agreed 95 and 96 percent. So a Google value that comes only from the shared file counts only when a maintained per-carrier source gives the same APN value, ignoring letter case, for that type on the same network code, under any MVNO selector: a Google per-carrier file, or a Samsung build at most three years old. It also counts when Google's frozen Pixel copies (TheMuppets) show that Google edited the entry's values for that type: a copy of the same entry, with the same network codes and MVNO selector, gives a value for the type that the current file no longer gives. Then every value the current file gives for that type counts. Only APN values are compared, ignoring letter case; a change of proxy or another setting, or a value Google only added, does not count, and there is no age cutoff, because TheMuppets dates are snapshot dates. So DENT's `global.telcoequity` (GID `3597BFD533`), which replaced `global.dentwireless` after the Pixel 3 files of 2022, keeps the lead over its own old copy and an Apple bundle re-issued in 2020. Otherwise the evidence index names Google in the fact's `shared_file_sources`, and the value counts like an old copy's. On Vodacom Tanzania (64004) Google's shared-file `Wap` row, with a WAP proxy, no longer leads; Samsung's current builds give `internet`. Frozen copies do not count as current: the TheMuppets Pixel vendor files, Sony's and Fairphone's trees. Nor do LineageOS's list, which keeps whatever nobody removed, and Apple's index, which keeps retired bundles: its date is the day a bundle was re-issued, not the day its content was written. Measured on 2026-10-06, Apple's newest bundles carry APNs made for iPhones (Vi `iphone`, Rogers `rogers-core-appl1.apn`) and old names carried forward (A1 Serbia `vipmobile`), and agree with the Android vendors' values less often than bundles one to five years old. On O2 Germany (26203) the only `ia` row was Fairphone's frozen E-Plus row, `internet.eplus.de`; it keeps `default` and `supl`, and a phone now attaches with `internet`, as current Google, Samsung and Apple configurations do. The E-Plus APN stays in the file because living brands still use it.
5. It ranks each scope. A row's lead type is the first of `default`, `ia`, `mms`, `ims`, `supl`, `dun`, `xcap`, `emergency` and the remaining types that it serves, so every row that serves the internet leads with `default`. Rows come in that order of lead type. Within one lead type, these questions decide, in this order:
   1. Is the APN a real name? An APN literally named `default` comes after real names. Several lists write it where they know no APN for the network. So does a malformed value, one with a character other than letters, digits, `.`, `-` and `_` (the APN syntax of 3GPP TS 23.003, with underscore tolerated), such as `mms/airtel mms` or `http://mms.pepephone.com`: Android passes it to the modem unchanged, and a network that checks the APN rejects it. Such a value is kept, not dropped or rewritten, because a network that overrides the APN accepts it, so it leads only where no valid value serves its type. On 2026-10-06 that was 12 scopes, among them 9 whose only MMS row has a malformed value.
   2. Does a current vendor (step 4) give this APN value for this type in this scope? Such a value comes before values only other sources give. This puts AT&T's current `nxtgenphone` before `broadband`, which more old copies give, and Tele2 Sweden's `internet.tele2.se` before `4g.tele2.se`, which only a Samsung build from before 2023 gives.
   3. For rows that serve the internet: does the row carry an HTTP proxy? A row without a `proxy` comes before a row with one. Android makes an APN's proxy the HTTP proxy of the data connection, and without a preferred APN it tries the internet rows in file order and keeps the first that connects as the preferred APN. So a WAP row with a proxy that came first and connected stayed in use even where its WAP gateway no longer works. Behind a proxy-free row the proxied row stays in the file as a fallback; no row loses `default`. Vendors order their files the same way: on 2026-10-06, 42 of the 44 Google per-carrier entries with a proxied internet row also ship a proxy-free one, first in raw file order in 10 of 11 files, and so do 24 of 28 such entries of Samsung builds of three years or less. The question comes after question 2, so a value a current vendor gives still comes first with its proxy: Orange Mali (61002) keeps Google's `wap`, its only internet value. An MMS proxy (`mmsproxy`) never counts, and rows that lead with another type never move. On 2026-10-06 the question changed the first internet row in 45 of 5,958 scopes, all to a row without a proxy, such as `internet` before Airtel Ghana's `wap` (62006) and `bsnlnet` before BSNL's `bsnllive` (40439, 40465); scopes whose first internet row carries a proxy went from 116 to 71. No row was removed or retyped.
   4. How many independent source families give this APN value for this type in this scope? The LineageOS, Sony and Fairphone lists descend from AOSP's list and count as one family, as do the two Google lanes and Samsung's two firmware lanes.
   5. Does a primary APN source give this APN value? Primary sources ship a phone's whole APN list: LineageOS, Fairphone, Sony, Samsung OMC, Apple and the two Google lanes. GNOME's mobile-broadband-provider-info, a menu users pick from, and the AOSP, LineageOS device overlay and Samsung IMS lanes are not primary.
   6. Does a current vendor back this exact row? Among the variants of one APN value, the one a current Pixel or Galaxy ships, with its protocol, types and other settings, comes first.
   7. How many families back this exact row?
   8. Does a primary source back this exact row?
   9. How many sources back this exact row?

   Rows still tied keep APN, type and label order.
6. It sends MMS to a current vendor's MMS row that serves a mobile network. Android sends MMS over the internet connection when the internet APN serves `mms`, and otherwise over the first row that serves `mms` on the current network type; the MMS service then reads the MMSC, MMS proxy and MMS port from that APN. A vendor MMS row is a row a current vendor backs for `mms`, with a real APN and an MMSC, that serves a 3GPP data network type: GPRS, EDGE, UMTS, HSDPA, HSUPA, HSPA, LTE, HSPA+ or NR, read from `network_type_bitmask`, else from `bearer_bitmask`, and all of them when a row has neither. It counts only for the types it serves, so a Wi-Fi-only or CDMA-only row never counts. When a scope has one, the first internet row loses `mms` if no current vendor backs it for MMS and the vendor MMS rows together serve every such type it serves; otherwise it keeps `mms`, so no network type is left without MMS. Then, if the first row that still serves `mms` is neither that internet row nor a vendor MMS row, the best vendor MMS row that serves neither `default` nor `ia` moves just before it. Only the first internet row is retyped: retyping every row no vendor backs lets Android merge EE's stale T-Mobile rows in 234/30. The profile JSON keeps the sources' types; `metadata.json` counts the retyped rows as `omissions.mms_types_left_out_not_vendor_backed`. Measured on 2026-10-08 on public `575632c1` with a model of TelephonyProvider and DataProfileManager, per network type: 7 first internet rows lose `mms` and one row moves in each of 102 scopes; no row is removed, and no internet or attach row changes on a phone; on LTE, NR, HSPA, UMTS and EDGE, MMS moves in 31 scopes, each to a current vendor's exact MMS setting (34 on all 11 network types), and no scope loses MMS. EE (234/30) now sends MMS over `eezone` and Telekom Germany (262/01) over `hos`, each with its MMSC and MMS proxy unchanged; Verizon's `VZWAPP` moves ahead of Google's CDMA-only `internet` row. Without the network types the rule left Bell's and Lucky's GID 40 and 42 scopes (302/630, 302/640) without MMS on every mobile network, because Google's only Bell MMS row, `apps.bell.ca`, is Wi-Fi only; those scopes keep their MMS row.
7. It writes the rows Android stores as one next to each other, the best-ranked last. TelephonyProvider stores rows that are equal on its unique fields as one row. Those fields are the network code, APN, proxy, port, MMS proxy, MMS port, MMSC, `carrier_enabled`, `bearer`, the MVNO selector, `profile_id`, both protocols, `user_editable`, `apn_set_id`, the carrier id, `infrastructure_bitmask` and `esim_bootstrap_provisioning` (`CARRIERS_UNIQUE_FIELDS`), compared as exact strings. Username, password, auth type, MTU, server, label and the bitmasks are not among them. The stored row keeps the first row's place, unites the types, merges the bearer and network type bitmasks, and takes every attribute a later row writes. So the file writes each such group once, at the place of its best-ranked row, with that row last and the others before it in reverse rank order: the phone stores the best row's values, and from the others only what the best row leaves unset. No row is removed and no value changes. A group's first row in the file is therefore not what the phone uses; `tools/resolve_carrier_profiles.py --explain` marks each row written before its group's best row (`stored_with_best_row`). Merging such rows into one row in the file was deferred: on 2026-10-06 it took usernames and passwords off 29 internet, 13 MMS and 20 attach leads on phones, some of which current Samsung builds ship. Measured on 2026-10-07 on public `c57ba1b2` with a model of TelephonyProvider's and DataProfileManager's merges: a phone stores the same 23,680 rows in the same order with the same types and bitmasks, and its first internet, MMS or attach row changes in 29 of 5,958 scopes (internet 19, MMS 21, attach 8), only in values the best row writes. No username or password is added or removed, and no APN value or HTTP proxy changes: Lycamobile France (20825) stores the user `lmfr` instead of the typo `Imfr`, Yettel Hungary (22001) `yettel` instead of `telenor`, and Personal Argentina (722340) PAP `datos`/`datos` instead of `gprs`/`adgj`. Whether credentials are sent follows the best row's auth type: they start on 3 internet leads (21401, 22601, 722340) and stop on 4 (26801, 26891, 26892, 28602), where Google and Samsung give auth type 0. The only MMSC change is Loop Mobile (40421), closed in 2014. The first rows read from the file change in 264 internet, 265 MMS and 224 attach scopes; those are not changes on a phone.
8. It leaves out a stale MMS-only row that Android merges into another row. DataProfileManager merges two stored rows into one profile when `ApnSetting.similar` holds: the same APN, no shared type, neither serving `dun`, proxy, MMSC, MMS proxy, credentials and MTU unset on one side or equal, and the auth type (an unset one resolved to 0 without a username and 3 with one), protocols, bitmasks and the remaining settings equal. The merged profile sits at the earlier row's place and takes the later row's MMSC, so a stale MMS row merged into the internet row sends MMS to its old MMSC ahead of the vendor's MMS row; and because the loop compares every later row with the earlier row as it was read, when several rows are similar to one row the last one wins and replaces the merges before it. So `apns-conf.xml` leaves out a stored row (every file row Android stores as one) when it serves only `mms`, its MMS setting (APN, MMSC, MMS proxy, MMS port) is no vendor MMS row's (step 6) in the scope, the vendor MMS rows together serve every mobile network type it serves, and it is similar to an earlier stored row of the scope. A phone never keeps such a row as a profile of its own, and the vendor's rows already serve every network it served, so this stays right if Android stops merging. The profile JSON keeps these rows; `metadata.json` counts them as `omissions.mms_rows_left_out_absorbed_by_android`. Measured on 2026-10-08 on public `152c3312` (step 6 merged, data of #191), per network type: 50 MMS-only rows in 39 scopes are left out, every one absorbed or replaced on a phone, and the phone stores 23,851 rows instead of 23,900; phone MMS moves to a current vendor's exact MMS setting in 15 more scopes on all 11 network types, among them O2 UK Pay & Go (234/10), O2 Ireland (272/02) and Spark NZ (530/05, 530/99), where the stale row had merged into the internet row; no scope loses an internet, MMS or attach profile, and no internet or attach row changes its APN, proxy, credentials, auth type, protocols or network types. Writing the merged profile into the file instead was rejected: it changes nothing on today's phones and would publish values from other rows.

A row is backed for a type by the sources whose observations support that fact: the `fact_sources` entry the evidence index lists for it, or every source of the profile when it lists none. [data-model.md](data-model.md) gives the key. The ranking reads nothing else, so anyone with the public files can reproduce it.

The rule changes the order and, in steps 4 and 6, one type; it leaves out only the rows of step 8, which a phone never keeps as profiles of their own. Every distinct APN value a source gives stays in the file, and so does every variant that differs in more than a label or a covered type set. No row is dropped for its brand or age, and there is no list of retired brands: a retired brand's APN simply ranks after the current vendors' values and no longer attaches. That keeps the APN variants rule above: sources that disagree still get every variant published and recorded as `published_variants`. Before this rule the variants were ordered by APN name, so the variant that sorted first was tried first, and on many networks that was a row named `default`. Now a value a current vendor ships is tried first, then the variant most sources back, and a primary source's row comes before a row only a menu source gives when the families tie. Collapsing only removes rows Android would have merged on load anyway. On 2026-10-06 step 4 took `ia` off 242 rows, and the current-vendor questions changed the first internet APN in 85 of 5,960 scopes, the first MMS APN in 45 and the attach APN in 117; with the row variants, the first internet row changed in 240 scopes and the first MMS row in 183. The row count stayed 25,382. `tools/resolve_carrier_profiles.py --explain` says for each row whether a current vendor gives its value (`value_from_current_vendor`) or backs the row itself (`row_from_current_vendor`), whether it is an internet row without an HTTP proxy (`proxy_free_first`), whether it lost `ia` (`ia_left_out`), whether the first internet row lost `mms` (`mms_left_out`) or kept it because no vendor MMS row serves all its network types (`mms_kept_no_vendor_coverage`), whether a vendor MMS row moved ahead (`vendor_mms_ahead`), and whether Android stores it as one with a better-ranked row written after it (`stored_with_best_row`); it lists the rows step 8 left out under `left_out` (`absorbed_mms_left_out`).

The generator reads `generated/evidence-index.json` next to its output, or the file `--evidence-index` names. Without it every row ties, so rows fall back to APN order, with placeholders last, and no row loses `ia`.

## Why profiles are neutral

A profile says "the carrier tables behind this SIM configure these settings". It is a configuration, not a test result. It does not say "Samsung says this" or "Apple says this". One reason drives that choice.

A consumer needs one answer per SIM. A ROM cannot ask the user which vendor to believe.

The cost is real. When sources disagree, the consumer gets nothing for that key. The evidence index shows why, so a maintainer can go back to the sources.

## Why an MVNO can land in its host's profile

Grouping by exact match set has one visible consequence. An MVNO that no source distinguishes from its host network merges into the host's profile.

LIDL Connect runs on the Vodafone Germany network, `26202`. No source names it with an SPN, GID, or IMSI prefix. So no profile names it. A LIDL Connect SIM resolves the plain `26202` profile plus whichever `26202` SPN profile matches the SPN on the SIM. The result is Vodafone's data, which may or may not be right for that MVNO.

The limit exists because the sanitizer only publishes what a source observed. It does not invent a selector. A maintained source that publishes a tested SPN or GID prefix, or an importer/mapping change, is the way to add one.

## What the 180-day window measures

Every source snapshot carries two dates. `revision_date` says when the upstream revision was published. `checked_at` says when automation last fetched the source with success: it is the last successful sync of that lane, a liveness date. It does not say that the values inside are still right. An unchanged source keeps passing as long as its lane runs, and an APN row last changed in 2010 passes with it.

The private sanitizer quarantines an observation when its source's `checked_at` or its own review date is 180 days old or more; observations carry no `checked_at` of their own. Vendor observations must also name how their freshness was proven, and only two lanes actually ask the vendor whether a setting is current: Samsung, whose firmware build Samsung's update service must confirm as current, and the GrapheneOS Pixel lane, which checks every Pixel against Google's live update service. Other vendor data, such as the Pixel vendor files from LineageOS's `TheMuppets` mirrors, passes as a versioned artifact at any age.

The public side publishes the result as a window. `checks_through` is the oldest `checked_at` and review date among the observations that survived quarantine. `stale_after` is `checks_through` plus 180 days, a lane-liveness deadline. Both sit in `generated/android/metadata.json`, in the header of the XML files and per profile in `generated/android/lookup.json`. `tools/generate_android_outputs.py` copies them from `generated/evidence-index.json` when the sanitizer publishes them there and computes them otherwise. `tools/validate_public_carrier_data.py` checks that the pair agrees with every snapshot date, then compares the UTC date with `stale_after`; it trusts the published `stale_after` and does not re-check each `checked_at` against 180 days. `tools/validate_device_catalog.py` does the same with `generated_from_checks_through` plus 180 days.

Stale is worse than missing. A missing APN row makes a phone fall back to its own defaults or ask the user. A stale row looks authoritative and sends the phone to a dead MMSC. Nobody notices until messages fail. So the project drops what a dead lane last said, drops rows LineageOS removed unless a newer source still gives them, and publishes how old the rest is (next section).

`checks_through` is the oldest of the snapshot checks and the observation review dates. The snapshot records are re-checked weekly, so the oldest Samsung observation sets it: an observation from a superseded firmware build keeps its July 2026 date until a daily Samsung run re-extracts it, and what is still from 2026-07-14 on 2027-01-10 is quarantined then. Because the limit counts the day it is reached, `stale_after` is the day that day's publish sets the oldest observation aside, so the 04:17 UTC alarm never sees a snapshot past `stale_after` while that day's publish was still to come. Past `stale_after` the validators warn by default and exit 0, so a clone keeps validating. The daily public job passes `--freshness fail`, and `--liveness fail`, which fails when one lane's source was not checked within its limit (10 days for the daily Samsung lanes `samsung_omc` and `samsung_ims`, 21 days for every weekly lane) or the last publish is more than 21 days old; a failure opens an issue labeled `stale-data`. Run this command to see the window:

```bash
python3 -c 'print(*[__import__("json").load(open("generated/android/metadata.json"))[k] for k in ("checks_through", "stale_after")])'
```

## How old the entries behind a fact are

A check date says when automation last confirmed a source. It does not say how old the entries inside that source are. A source checked last week can still carry an APN row last changed in 2010.

So each observation also records the date of the newest upstream entry behind it. An entry is one APN row, one provider block, one CarrierConfig file or block, one Pixel carrier file, one Apple bundle, or one Samsung CSC package. The git-based lanes use the first day they saw the entry's current content, seeded from git history. Apple uses the publish date in the bundle's download URL from Apple's index. Samsung uses the build month in the CSC build string. Every date is the latest possible one, so an age read from it is a minimum. When no date can be found, none is published.

The evidence index publishes the result to the month. `newest_entry` is the newest entry behind a profile, and `generated/android/lookup.json` repeats it per profile. `capability_newest_entries` gives it for each capability a source gives a value, also one a gate publishes as `unknown`. Both appear only where every supporting observation is dated. `flags` marks a capability whose value rests on one family with an entry over five years old as `old_single_source`; flags withhold nothing. Until 2026-10-06 a second flag, `capability_label_withheld`, marked a capability-gating CarrierConfig key published next to a withheld label; such a key is now left out. On 2026-10-04, 1,009 of 7,806 profiles have no entry newer than September 2021, more than five years old; 645 of them rest on Apple bundles alone and 129 on AOSP alone, and 711 of them put 1,056 APN rows into `apns-conf.xml`. Run this command to print the oldest dated capabilities, published or withheld:

```bash
python3 -c 'import json; e=json.load(open("generated/evidence-index.json")); print(*sorted((d, k, p["profile_id"]) for p in e["profiles"] for k, d in p.get("capability_newest_entries", {}).items())[:10], sep="\n")'
```

How to read the age of a value: it is older when every source behind it is a frozen copy (TheMuppets' Pixel trees, Sony's tree, Fairphone's tree) or an old build (`old_build_sources`). `capability_sources`, `fact_sources` and `sources` name the sources behind each value, and `capability_newest_entries` and `newest_entry` give the month. There is no separate age flag: a date records the last change of an entry, not a confirmation that it is still right.

Old is not always wrong, and age is a gradual signal, not a five-year step. A review on 2026-10-05 compared old "supported" capabilities with fresh data from another source family. They agreed on VoLTE 94.4 percent of the time (0.5 percent contradicted), VoWiFi 86.3 (0.8), video calling 91.5 (5.2) and MMS 95.4 (4.2). Disagreement grows with age, from claims under one year old to claims over five (VoLTE 2.7 to 6.7 percent, VoWiFi 6.2 to 16.9, video calling 5.6 to 10.6, MMS 1.0 to 3.6), but most of the rise happens before three years: claims over five years old agree about as often as claims three to five years old. So the five-year limit is a cut on a slope, and since 2026-10-06 age alone withholds only video calling, of whose 82 old single-source values fresh data contradicted 8 and confirmed 1. An old single-source VoLTE, VoWiFi, MMS or Wi-Fi calling while roaming value is withheld only when its one source is a frozen copy or no fresh observation covers the profile's scope, as described above. On 2026-10-06 that withholds 714 values instead of 895: 82 video calling values for their age, 46 values only Sony's frozen tree gives, and 586 that no fresh observation covers, most of them in SIM-specific profiles that only an old Apple bundle, LineageOS device overlay or AOSP list describes. 181 values that age alone had withheld are published as `supported` again. A withheld capability is published as `unknown`, keeps its date, and is flagged `old_single_source`. Since 2026-10-06 the CarrierConfig key that switches the same feature on is left out with it: the label and the switch say the same thing, and a ROM that applies `carrier-config-list.xml` keeps its own value for the key. That left out 486 keys, 127 of them in `carrier-config-list.xml` (`carrier_vt_available_bool` 45, `carrier_wfc_ims_available_bool` 34, `carrier_volte_available_bool` 32, `enabledMMS` 16), and withdrew 2 profiles whose last facts they were. APN rows and CarrierConfig values only show their age. That is not because they agreed more often: in the study of 2026-10-03 CarrierConfig values agreed 76 percent of the time, less than VoWiFi (88) and video calling (80) on that study's measure.

## What the public repo checks

The workflow `Validate carrier data` in `.github/workflows/validate.yml` has two jobs. `validate` runs on push to `main`, on pull requests, and on manual dispatch. It validates the profiles against the stable index and the device catalog in warn mode, runs the test scripts, and regenerates `generated/android/` to confirm nothing drifted. Then it checks `generated/android/apns-conf.xml` with `xmllint` against LineageOS's `apns-conf.xsd`. `tools/lineageos/apns-conf.xsd` is a byte copy of that schema at LineageOS `android_vendor_apn` revision `6e73ba90`, Apache-2.0 like the rest of the tools. It is the required check on `main`. Pull requests, including carrier-data ones, are untrusted input: they run through the `pull_request` trigger with a read-only token (`permissions: contents: read`), and the workflow uses no secrets. `freshness-alarm` runs daily at 04:17 UTC by cron and on manual dispatch. It runs both validators with `--freshness fail`, and the carrier validator also with `--liveness fail`: that fails when any lane's `checked_at` in `source_snapshots` is older than that lane's limit, or the last commit titled `Update sanitized carrier data` on the validated branch is more than 21 days old. The limit is 10 days for the two Samsung lanes, `samsung_omc` and `samsung_ims`, which run daily on the self-hosted runner and whose manifest can lag up to six days (`LANE_LIVENESS_MAX_AGE_DAYS`), and 21 days for every other lane (`LIVENESS_MAX_AGE_DAYS` in `tools/validate_public_carrier_data.py`). Every weekly import re-checks its sources and every check reaches this repo through a publish, so 21 days means three missed weekly runs; `stale_after` alone would notice a stopped pipeline only about six months later. Each lane is checked on its own, so one dead lane shows even while the others keep publishing. While a Samsung build publishes under the vendor build grace (`vendor_build_grace` in the evidence index: a new build of the tracked firmware appeared and the IMS and CarrierConfig indexes were not yet rebuilt from it, so the previous build's values keep publishing for up to 30 days), the liveness check warns every day and the job shows the warning on the run; once the build's last confirmation is more than 10 days old it fails like a stopped Samsung lane, which leaves about 19 days to fix the refresh before the values drop. For a deliberate pause, the repository variable `LIVENESS_SNOOZE_UNTIL` (a date) turns the liveness failure into a warning up to that day. When the validators fail it opens one issue labeled `stale-data` with the validator output, and it does not open a second while one is open. When they pass again it closes that issue. It is the only job with `issues: write`, and it never runs on a pull request. The dispatch input `simulate_today` passes `--today` to the validators, so the alarm can be rehearsed before the real date arrives. GitHub disables a public repository's scheduled workflows after 60 days without a commit and emails the owner first. Every data publish is a commit to `main`, so the alarm keeps running while publishes land, and `gh workflow enable validate.yml` turns it back on after a pause.

The `validate` job also runs a phone-level guard, `tools/check_phone_guard.py`, on every pull request whose `apns-conf.xml` differs from its base (rule decisions of 2026-10-06, publish guard of 2026-10-08). It reads the base's and the head's file with `tools/android_phone_model.py`, a model of what an Android phone makes of the file: TelephonyProvider's merge of equal rows, ApnSetting and DataProfileManager's dedupe, read from the LineageOS sources. For every scope in both files and every 3GPP data network type (GPRS, EDGE, UMTS, HSPA, HSPA+, LTE and NR) it holds four changes: the scope loses its internet lead, loses its attach lead, loses working MMS (a route with an MMSC), or MMS moves from a current vendor's tuple (APN, MMSC, MMS proxy, MMS port, from the generator's own records of the head) to one no current vendor gives; APN names and MMSCs are compared case-folded, and a trailing `/` on the MMSC is ignored. Everything else it only reports: credentials and HTTP proxies on the leads, a lead moving to an APN no current vendor gives, scopes that leave the file, losses only on Wi-Fi (IWLAN) or CDMA types, other MMS moves, stored-row counts and `persist_apns_for_plmn` events. A hold fails `validate`, so the pull request cannot merge. It prints each trip with its network types and old and new values, then a digest: the first 16 hex characters of sha256 over the sorted trip lines. The trips pass only when the pull request body has the exact line `phone-guard-accept: DIGEST` for them; `validate` also runs when the body is edited, so adding the line checks again. Any other or changed trip changes the digest, and there is no other bypass. A data publish that trips is opened as a draft labeled `publish-held` and stays unmerged until later data or a generator fix removes the trip, or the private publish workflow is dispatched with that digest; the data already on `main` stays live meanwhile, and nothing releases on a timer.
